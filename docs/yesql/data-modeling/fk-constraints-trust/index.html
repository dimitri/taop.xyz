Foreign Key Constraints and What the Planner Knows

A foreign key is not just validation — it is a declaration that tells the query planner something is guaranteed, enabling optimizations it cannot safely make without that guarantee.

Run it yourself — all queries on this page use the chinook, f1db datasets, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

The chinook and f1db schemas contain similar kinds of data — music tracks and race results, both with artists/drivers, albums/races, and a hierarchy of related entities. But they are designed differently in one important way: chinook enforces foreign keys everywhere; f1db has none.

You can see the difference in the catalog:

select cl.relname                   as table_name,
       pg_get_constraintdef(c.oid)  as definition
  from pg_constraint c
       join pg_class     cl on cl.oid = c.conrelid
       join pg_namespace n  on n.oid  = c.connamespace
 where n.nspname  = 'chinook'
   and cl.relname = 'invoiceline'
   and c.contype  = 'f';

 table_name  │                          definition
═════════════╪═══════════════════════════════════════════════════════════════
 invoiceline │ FOREIGN KEY (invoiceid) REFERENCES chinook.invoice(invoiceid)
 invoiceline │ FOREIGN KEY (trackid) REFERENCES chinook.track(trackid)
(2 rows)

This returns two rows: invoiceline has a foreign key to invoice and another to track. The planner knows that every invoiceline.trackid is guaranteed to match exactly one row in track. That guarantee is usable.

What the planner can do with it

When a foreign key exists, the planner can safely eliminate joins. If your query joins invoice_line to track but selects no columns from track and applies no filter on track, the planner can skip the join entirely — the FK proves the join would not remove any rows.

Without a foreign key, the planner cannot make that assumption. An unconstrained trackid column might contain values that match no track row, or it might be NULL. The join must happen to find out.

For f1db — no foreign keys — the planner cannot apply these optimizations. It must treat every join as potentially row-filtering, even when you know (from domain knowledge) that the data is clean. The planner only knows what you declared, not what you know.

Constraints as documentation

Foreign keys also document intent. A schema with constraints makes it obvious which columns reference which tables, what the cardinality is, and which deletes cascade. A schema without constraints requires reading application code or talking to the team to understand the same things.

The cost of a foreign key is an index on the referencing column (to make the referential integrity check fast) and a constraint check on every insert and update. In most OLTP workloads that cost is negligible. The benefit — both for correctness and for planner trust — is not.
