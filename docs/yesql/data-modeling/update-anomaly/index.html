The Update Anomaly: Why Normalization Matters

Storing the same fact in more than one row creates a predictable failure mode: a partial update leaves the database inconsistent, with no way to know which copy is correct.

Run it yourself — all queries on this page use the f1db dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

Wikipedia’s definition of a database update anomaly:

“The same information can be expressed on multiple rows; therefore updates to the relation may result in logical inconsistencies.”

That sounds abstract. Here is what it looks like in practice.

The F1 example

The f1db.drivers table stores each driver’s nationality as a plain text string directly in the row — 'British', 'German', 'French'. It is not a foreign key to a separate nationalities table. It is just a repeated string.

select nationality,
       count(*) as drivers,
       'renaming ''' || nationality || ''' requires updating '
           || count(*) || ' rows'
       as anomaly
  from f1db.drivers
 where nationality in ('British', 'German', 'French')
 group by nationality
 order by drivers desc;

 nationality │ drivers │                    anomaly
═════════════╪═════════╪═══════════════════════════════════════════════
 British     │     162 │ renaming 'British' requires updating 162 rows
 French      │      73 │ renaming 'French' requires updating 73 rows
 German      │      49 │ renaming 'German' requires updating 49 rows
(3 rows)

The anomaly column makes the problem concrete: renaming 'British' to 'English' requires touching every row for every British driver. If the UPDATE is interrupted — network timeout, application crash, batch job stopped mid-run — some rows say 'British' and others say 'English'. The database now records two answers to the same question with no way to determine which is authoritative.

Nationality is not a fact about a race result. It is a fact about a driver. Storing it once per result row, or even once per driver row without referential integrity, means the same fact lives in multiple places and can diverge.

The fix

A normalised design puts nationality in a separate table — one row per nationality — and references it by foreign key. The rename becomes a single UPDATE on one row. Every reference picks up the change automatically. Consistency is guaranteed by construction, not by discipline.

The other two anomalies

Update anomaly is the most common but not the only one. The related failures are:

  • Insertion anomaly: a fact cannot be recorded at all unless another unrelated fact is also present (you cannot add a new circuit to F1 until at least one race has been held there).
  • Deletion anomaly: deleting one fact also deletes another (removing the last race at a circuit deletes the circuit itself from the database).

All three anomalies have the same root cause: a fact stored in the wrong place relative to its natural entity. Normalization is the discipline of finding where each fact belongs and storing it exactly once.
