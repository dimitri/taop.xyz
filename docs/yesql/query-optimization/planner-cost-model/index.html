How the PostgreSQL Planner Picks a Plan

The planner assigns a numeric cost to every possible execution strategy and picks the cheapest. Understanding how it calculates cost explains why it sometimes picks what looks like the wrong plan.

Run it yourself — all queries on this page use the f1db dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

When you run a query, PostgreSQL does not just execute it. First, the planner enumerates the ways the query could be executed — which indexes to use, which join algorithm to apply, in what order to process tables — and assigns a cost to each option. The option with the lowest cost wins.

That cost is not a time in milliseconds. It is a dimensionless number, calibrated relative to seq_page_cost = 1.0. You can inspect the current settings:

select name,
       setting,
       unit,
       short_desc
  from pg_settings
 where name in (
         'seq_page_cost',
         'random_page_cost',
         'cpu_tuple_cost',
         'cpu_index_tuple_cost',
         'cpu_operator_cost',
         'effective_cache_size',
         'work_mem'
       )
 order by name;

         name         │ setting │ unit │ short_desc

                      │         │      │ processing each operator or function call.

                      │         │      │ processing each tuple (row).

The two most important parameters are seq_page_cost (reading data pages sequentially from disk or cache) and random_page_cost (random I/O, typical of index lookups). Defaults are 1.0 and 4.0.

Why this ratio matters

When random_page_cost is high (4.0, tuned for spinning disks), the planner prefers sequential scans — reading every page in order — over index scans that jump around. On SSDs, random I/O is much cheaper, and random_page_cost of 1.1 or 1.5 is more appropriate. Miscalibration here is one of the most common reasons the planner picks a sequential scan on a table that clearly has a useful index.

What the planner knows

The planner’s decisions depend on statistics collected by ANALYZE: estimated row counts per table, null fractions, most-common values, and histograms. From these, it estimates how many rows each predicate will match. When estimates are wrong — stale statistics, unusual data distributions, correlated columns — the planner can choose a bad plan even with correct cost settings.

The takeaway

If you find yourself fighting the planner — it picks a sequential scan when you expect an index scan, or a nested loop when a hash join would be faster — the diagnosis almost always comes down to one of three things:

  1. Wrong cost settings — random_page_cost not calibrated for your storage
  2. Stale statistics — run ANALYZE tablename
  3. Bad estimates — complex predicates the planner cannot accurately model

EXPLAIN tells you which plan was chosen and at what estimated cost. EXPLAIN ANALYZE tells you whether the estimates were right. Start there.
