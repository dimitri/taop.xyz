Predicate Pushdown: Filter Close to the Scan

PostgreSQL automatically moves WHERE conditions as close to the underlying scan as possible. Understanding when it can't — and why — is a key query-rewriting skill.

Run it yourself — all queries on this page use the f1db dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

The principle is simple: filter rows as early as possible. Fewer rows entering a join or an aggregation step means less work. PostgreSQL’s planner does this automatically — it is called predicate pushdown — but certain query patterns block it.

The happy path

This query asks for the winner of every 2017 race:

explain (analyze, buffers)
select r.name, r.date,
       d.surname as winner
  from f1db.races   r
  join f1db.results res on res.raceid        = r.raceid
                       and res.positionorder = 1
  join f1db.drivers d   on d.driverid       = res.driverid
 where r.year = 2017;

 Hash Join  (cost=36.45..747.98 rows=20 ...)
   Hash Cond: (res.raceid = r.raceid)
   ->  Seq Scan on results res  (... rows=974 ...)
         Filter: (positionorder = 1)
   ->  Hash  (... rows=20 ...)
         ->  Seq Scan on races r  (... rows=20 ...)
               Filter: (year = 2017)
               Rows Removed by Filter: 956

The WHERE r.year = 2017 predicate filters the races table. The planner pushes it down to the scan, so only 2017 races enter the join — not all 1,000+ races in the table. The join then only needs to look up results for those twenty races.

When CTEs block pushdown

Pre-PostgreSQL 12, a CTE was always an optimization fence: the planner would fully execute the CTE, materialise the results, and only then apply outer predicates. Rewriting the query with a CTE meant the planner lost the ability to push r.year = 2017 into the inner scan.

Since PostgreSQL 12, CTEs are inlined by default — the planner treats them like subqueries and can push predicates through. But if you write WITH ... AS MATERIALIZED, you force the old behaviour: the CTE executes independently, and predicates from the outer query cannot reach inside it.

-- With MATERIALIZED, the planner cannot push year = 2017 into this CTE:
explain (analyze, buffers)
with winners as materialized (
  select res.raceid, res.driverid
    from f1db.results res
   where res.positionorder = 1
)
select r.name, d.surname
  from winners w
  join f1db.races   r on r.raceid   = w.raceid
  join f1db.drivers d on d.driverid = w.driverid
 where r.year = 2017;

 Nested Loop  (cost=745.69..775.53 rows=20 ...)
   CTE winners
     ->  Seq Scan on results res  (... rows=974 ...)   ← scans ALL years
           Filter: (positionorder = 1)
   ->  Hash Join  (... rows=20 ...)
         ->  CTE Scan on winners w  (... rows=974 ...)  ← sees full materialised CTE
         ->  Hash  (... rows=20 ...)
               ->  Seq Scan on races r  (... rows=20 ...)
                     Filter: (year = 2017)

Here winners materialises all race winners from all years before the outer WHERE r.year = 2017 runs. The plan will be slower.

The rule

Reach for MATERIALIZED only when you want the CTE to execute once and be reused multiple times in the outer query, or when you need to prevent the planner from applying aggressive transformations (rare). For most CTEs, the default (inline) behaviour is what you want — let the planner push predicates through.

When a query is slow and EXPLAIN shows an unexpectedly large scan, check whether a CTE fence is preventing pushdown. Removing MATERIALIZED or rewriting as a subquery often fixes it immediately.
