WHERE vs HAVING: Filter Before or After the Group

WHERE filters rows before grouping; HAVING filters groups after aggregation. Confusing them produces wrong results or a syntax error.

Run it yourself — all queries on this page use the f1db dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

Here is the rule: WHERE runs before GROUP BY. HAVING runs after.

That is not just a syntax difference — it is an evaluation order difference. WHERE decides which rows enter the aggregation. HAVING decides which groups survive it. Expressions that reference aggregate function results (count(*), sum(...), avg(...)) cannot appear in WHERE because the aggregates have not been computed yet. They must go in HAVING.

A concrete example

The F1 database records every result from every race, including a status column for cars that did not finish. What were the most common reasons for retiring in the 1978 season — the most accident-prone era in the sport — appearing ten or more times?

  select status,
         count(*) as occurrences
    from results
         join races  using(raceid)
         join status using(statusid)
   where date between date '1978-01-01'
                  and date '1978-01-01' + interval '1 year - 1 day'
     and position is null
group by status
  having count(*) >= 10
order by count(*) desc;

       status       │ occurrences
════════════════════╪═════════════
 Did not qualify    │          55
 Accident           │          46
 Engine             │          37
 Did not prequalify │          25
 Gearbox            │          13
 Transmission       │          12
 Spun off           │          12
(7 rows)

The WHERE clause runs first and cheaply eliminates everything outside 1978 and all rows where the driver actually finished. Only the non-finishes enter the GROUP BY. The HAVING clause then looks at the groups and drops any status that occurred fewer than ten times.

If you tried to write where count(*) >= 10 you would get a syntax error: aggregate functions are not allowed in WHERE. Move it to HAVING and PostgreSQL computes count(*) once and reuses it in both the SELECT list and the HAVING clause.

The mental model

Think of a SQL query as a pipeline:

  1. FROM — assemble the rows (joins, subqueries)
  2. WHERE — filter rows
  3. GROUP BY — form groups
  4. Aggregate functions run over each group
  5. HAVING — filter groups
  6. SELECT — project columns
  7. ORDER BY / LIMIT

Put predicates as early in this pipeline as possible. A WHERE filter that eliminates 90% of your rows means 90% fewer rows entering the GROUP BY and the aggregation step. A HAVING filter that does the same work runs on the full input — slower, and sometimes wrong if the expression cannot even be evaluated before aggregation.

If a condition can be expressed without aggregate functions, it belongs in WHERE. Only conditions on aggregate results belong in HAVING.
