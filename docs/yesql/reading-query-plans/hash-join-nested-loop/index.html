Hash Join vs Nested Loop: What the Plan Node Tells You

Two join algorithms, two different performance profiles. The plan node tells you which one PostgreSQL chose and why — and when to question that choice.

Run it yourself — all queries on this page use the f1db dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

When PostgreSQL joins two tables it picks one of three algorithms. The plan node name tells you which one was chosen. Understanding the trade-offs helps you know when the planner made the right call — and when to give it a nudge.

Hash Join

A Hash Join builds a hash table from the smaller input (the inner side), then scans the larger input (the outer side) and probes the hash table for each row. The startup cost is the hash table build; after that, probing is fast.

explain (analyze, buffers)
select d.nationality,
       count(distinct d.driverid)                     as drivers,
       count(*) filter (where res.positionorder = 1)  as wins
  from f1db.results res
  join f1db.drivers d on d.driverid = res.driverid
  join f1db.races   r on r.raceid   = res.raceid
 where r.year = 2017
 group by d.nationality
 order by wins desc;

 Sort  (cost=820.05..820.15 rows=41 ...)
   ->  GroupAggregate  (Group Key: d.nationality)
         ->  Hash Join  (cost=77.37..790.85 rows=485 ...)
               Hash Cond: (res.driverid = d.driverid)
               ->  Hash Join  (cost=36.45..748.64 rows=485 ...)
                     Hash Cond: (res.raceid = r.raceid)
                     ->  Seq Scan on results res  (rows=23677 ...)
                     ->  Hash  →  Seq Scan on races r
                                   Filter: (year = 2017)
               ->  Hash  →  Seq Scan on drivers d  (rows=841 ...)
 Execution Time: 4.515 ms

For this query — joining results to drivers and races across all of 2017 — the planner uses a Hash Join. The drivers table is smaller than results; it becomes the hash table. Each result row probes into it. Total cost is high, but it scales linearly with input size.

You will see Hash Join in the plan output with a child node Hash below it. The Hash node is the build step; the probe happens at the join level.

Nested Loop

A Nested Loop iterates: for each row in the outer input, scan the inner input to find matching rows. Ideal when the outer set is small and the inner side has an index that makes each lookup fast.

explain (analyze, buffers)
select r.name   as race,
       r.date,
       res.positionorder,
       res.points
  from f1db.drivers  d
  join f1db.results res on res.driverid = d.driverid
  join f1db.races    r  on r.raceid    = res.raceid
 where d.driverid = 1
 order by r.date;

 Sort  (Sort Key: r.date)
   ->  Hash Join  (Hash Cond: res.raceid = r.raceid)
         ->  Nested Loop  (actual rows=203.00 loops=1)
               ->  Index Only Scan on drivers d
                     Index Cond: (driverid = 1)
                     actual rows=1.00 loops=1     ← outer set: one driver
               ->  Seq Scan on results res
                     Filter: (driverid = 1)
                     Rows Removed by Filter: 23474
 Execution Time: 1.936 ms

Here the outer set is one driver (one row). The inner results table is scanned with an index on driverid. With one outer row and a fast index lookup, Nested Loop is the clear winner — zero hash table build, one index probe.

The plan says Nested Loop with indented child nodes. loops=N in the inner node’s actual output tells you how many times the inner scan ran. If loops=1, you have a Nested Loop over a trivially small outer set. If loops=25000, you have a Nested Loop that ran 25,000 index probes — which may or may not be the right call.

What to look for

  • Hash Join with loops=1 and large inputs: usually correct. Check Batches — if > 1, the hash table spilled to disk and work_mem is too low.
  • Nested Loop with high loops=N and no inner index: the planner expected the outer set to be small but it was not. Check row estimates.
  • Merge Join: appears when both inputs are already sorted (or sorted by an index). No hash table, no nested scan — just a linear merge pass. Efficient when both inputs are large and pre-sorted.

The algorithm chosen is almost never wrong when the row estimates are right. When you see an unexpected algorithm, check the estimates first.
