EXPLAIN ANALYZE: Reading Actual vs Estimated Rows

The most important number in EXPLAIN ANALYZE is not the timing — it is the gap between estimated rows and actual rows. A large discrepancy means the planner made its decision on wrong information.

Run it yourself — all queries on this page use the f1db dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

EXPLAIN shows you what PostgreSQL plans to do. EXPLAIN ANALYZE shows you what it actually did. The gap between the two is where slow query diagnosis starts.

Every node in an EXPLAIN ANALYZE output has two sets of numbers:

  • Estimated: cost=startup..total rows=N width=B — the planner’s prediction before execution
  • Actual: actual time=startup..total rows=N loops=L — measured at runtime

The most useful comparison is rows= in the estimate versus rows= in the actual. When these are close, the planner had good information and likely chose a good plan. When they diverge by a factor of 10 or more, the planner was working with bad statistics and may have chosen the wrong join algorithm, the wrong index, or the wrong scan strategy.

A concrete example

explain (analyze, buffers)
select r.year,
       r.round,
       r.name
  from f1db.races r
 where r.year = 2017
   and r.round <= 10;

 Seq Scan on races r  (cost=0.00..38.64 rows=14 width=35)
                      (actual time=0.060..0.065 rows=10.00 loops=1)
   Filter: ((round <= 10) AND (year = 2017))
   Rows Removed by Filter: 966
   Buffers: shared hit=24
 Execution Time: 0.087 ms

In a fresh database this query returns 10 rows (10 races from rounds 1–10 of the 2017 season). If the statistics are stale — perhaps ANALYZE has not run since a large data load — the planner might estimate rows=1 or rows=200. Either way it produces the correct result. But a rows=1 estimate might cause the planner to pick a nested-loop join in a larger query that would run faster with a hash join.

Reading the output

A key line might look like:

Seq Scan on races r  (cost=0.00..4.64 rows=10 width=40)
                     (actual time=0.012..0.089 rows=10 loops=1)

rows=10 in the estimate and rows=10 actual — perfect. If the estimate said rows=1 and actual showed rows=10, that is a 10× miss and a warning sign.

The Buffers: shared hit=2 line (from the BUFFERS option) tells you how many 8KB pages were read from the cache versus from disk. High buffer hits are cheap; shared reads from disk are expensive. Large buffer reads on a small table are another signal to investigate.

When to add ANALYZE

EXPLAIN is safe to run anytime — it does not execute the query. EXPLAIN ANALYZE runs the query fully and reports real timing. For SELECT queries this is always safe. For INSERT, UPDATE, DELETE, wrap in a transaction and roll back if you do not want side effects:

BEGIN;
EXPLAIN ANALYZE DELETE FROM results WHERE raceid = 999;
ROLLBACK;

Start with EXPLAIN (ANALYZE, BUFFERS) as your default — the extra information costs almost nothing and is routinely decisive.
