A Map With No Graphics Library

Bin points into a grid, count them, and encode density as Braille height-bar characters — four dot-fill levels on fixed thresholds, and PostgreSQL draws a recognizable map straight into the query result.

Run it yourself — all queries on this page use the tweet dataset, pre-loaded in the free TAOP lab. Start a session with psql taop and follow along. No setup beyond Docker.

You don’t always need a plotting library to see your data. With nothing but GROUP BY, a little arithmetic, and Unicode Braille characters, PostgreSQL can draw a density map straight into the query result.

We use the tweet dataset (loaded with taop hashtag): 200,000 geolocated tweets from across the United States, each with a longitude and latitude.

The problem

Where are the tweets? We want a quick map of their density — no GUI, no client, just psql.

The idea

Divide the map into an 80×20 grid of cells. Count how many tweets fall in each cell. Then pick one of four Unicode Braille characters that encodes the density as a height bar built from dots: ⣀ fills only the bottom row of the cell (2 dots), ⣤ fills the bottom two rows (4 dots), ⣶ three rows (6 dots), and ⣿ fills all four rows (8 dots). Every occupied cell shows at minimum ⣀, so the full US landmass stays visible — the same contract as the PostGIS density map, which colours every land cell.

The query

with bounds as (
   select -125 as w, -66 as e, 24 as s, 50 as north,
          80 as cols, 20 as rows
), grid as (
   select gx as cx, gy as cy
     from bounds,
          generate_series(0, cols - 1) as gx,
          generate_series(0, rows - 1) as gy
), hits as (                              -- tweet count per cell
   select floor((longitude - w) / (e - w) * cols)::int as cx,
          floor((north - latitude) / (north - s) * rows)::int as cy,
          count(*) as c
     from tweet, bounds
    where longitude between w and e
      and latitude  between s and north
    group by 1, 2
)
select string_agg(
         case when c is null then '⠀'    -- no tweets
              when c > 250   then '⣿'    -- 8 dots — all 4 rows
              when c >  80   then '⣶'    -- 6 dots — bottom 3 rows
              when c >  20   then '⣤'    -- 4 dots — bottom 2 rows
              else                '⣀'    -- 2 dots — bottom row only
         end,
         '' order by cx)
  from grid
       left join hits using (cx, cy)
 group by cy
 order by cy;

How it works

Each of the four Braille characters is a height bar made of dots, filling from the bottom of the character cell upward:

Character Dots Rows filled Equivalent
⣀ 2 bottom row only any tweet
⣤ 4 bottom 2 rows c > 20
⣶ 6 bottom 3 rows c > 80
⣿ 8 all 4 rows c > 250

Unicode Braille (U+2800–U+28FF) packs a 2×4 dot matrix into each glyph — the eight dots are independent bits, so any combination is a valid character. The height-bar subset used here (bottom-up fill) mirrors ▂ ▄ ▆ █ but with visible dot structure instead of solid fills.

Crucially, every cell with at least one tweet shows ⣀, so the US landmass is visible even in the thinly-tweeted Great Plains — the same contract as the PostGIS density map, which colours every land cell.

It is the very same data PostGIS draws as a proper density map — only the rendering differs:

The point stands either way: a “map” is just a grid of counts, and SQL is very good at grids of counts.
